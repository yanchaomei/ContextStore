# 证据与详细报告

## 恢复本次输入

先定位实际仓库和已有交付物，读取适用的项目说明；项目要求语义搜索时先用对应
搜索工具。查看当前分支/提交、工作区变更和远端，区分代码、生成材料与只读参考。
不要把旧材料中的源码哈希、截止时间或环境说明直接当成本次状态。

在材料工作目录记录一份小型制作契约，字段按实际需要取用：

| 字段 | 应记录的事实 |
| --- | --- |
| 目标 | 比赛/赛道、受众、官方要求来源及查询日期 |
| 时间 | 截止的完整日期、时间、时区；本次计划的交付状态 |
| 版本 | 仓库、分支、commit、未提交修改、关键二进制/数据哈希 |
| 证据 | 运行日期、环境、命令、退出码、原始输出、负对照 |
| 材料 | 已有文件、本次保留/更新/新增、用户指定风格和声音 |
| 授权 | 已授权的生成、服务使用、实验、推送、外发及提交范围 |

制作记录中的本地绝对路径可用于本机操作；可分享的复现说明、脚本和包清单使用
相对路径或显式参数。凭据不进入任何制作记录。

## 主张到证据

每个有判定意义的主张应能追到一项可打开的依据。可用这样的台账：

| ID | 面向评委的主张 | 原始依据和位置 | 版本/日期/环境 | 可以证明 | 不能证明 |
| --- | --- | --- | --- | --- | --- |
| C1 | 使用项目实际措辞 | 日志、源码行、数据文件、官方文档 | 本次确认值 | 观测范围 | 尚缺的端到端或硬件证据 |

把“设计”“已实现”“正确性验证”“性能测量”“部署”“已提交/接受”作为不同
证据等级。软件仿真、虚拟机、组件通过或归档实验应在正文和视频中带上范围。
出现负结果时解释条件与结论，不剪掉失败样本来制造普遍优势。

精确数值应来自原始数据或可追溯计算。检查分母、单位、样本量、误差区间、基线
公平性和同版本条件。若只有已有实验而未重新运行，写明日期和“归档结果”。
外部论文/产品/官方规则以当前一手资料核实；访问失败记为无法核实。

## 让详细报告有内容

按项目取舍以下内容，而非逐项强制凑章节：

- 具体用户/任务、触发条件、现有方案的失败方式与设计目标。
- 一句话核心机制及完整请求/数据流；架构中的组件职责和边界。
- 输入输出、数据布局、版本/一致性规则、资源预算与成本。
- 正常执行、异常处理、取消/恢复、生命周期与适用前提。
- 关键接口和可运行示例；解释性代码标明未新编译/未实测状态。
- 实验配置、基线、统计方法、结果、负对照、失败案例与限制。
- 部署/演示步骤、依赖、复现入口、源证据索引与后续工作。

先补“为什么”和“具体怎样”，再判断是否需要新图或表。页数由内容和比赛要求
决定。用目录、书签、图表编号与来源编号帮助查阅；不同复杂度项目不共享固定
页数或章节数。

## 可编辑源与渲染

保留报告内容源、生成入口和依赖说明。已有可靠生成脚本可参数化复用；不要把
某次项目名称、服务器、字体绝对路径或用户目录复制成通用代码。

有表格和长代码时优先自动换行、重复表头、合理分组；保留可复制正文。检查中文
字体与缺字，修复转义造成的公式/比较符丢失。采用当前环境的 PDF/文档技能或
可用排版工具生成，随后渲染全部页面。仅阅读抽取文本不能证明版式正确。

每次修改后重建成品。至少核对全部页缩略图，详查密集表格、代码、图注、目录、
首尾页和改动页；检查裁切、重叠、空白、可读字号、链接/书签与来源。
记录实际检查的页码及文件哈希，避免将旧版审阅结论套到新版 PDF。
