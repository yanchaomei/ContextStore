**Why the port-reuse proof is sufficient.** The following chain is present in the frozen source, not inferred from matching totals:

1. In `recovery_campaign.rs:624–639`, the fault relay closes the client side, waits for the retry-registration gate, forwards the captured old request to the real server, requires actual EOF, records its frame, and only then marks `old_terminal`. A non-EOF result returns an error and cannot become the expected receipt.
2. At lines 641–648, the retry relay sets the registration gate only after receiving the complete retry frame, then waits for `old_terminal` before forwarding the retry request. At lines 896–1008 the control campaign runs one serial loop: it awaits the current client call, verifies exact output or the specific F0 error plus untouched sentinel, waits for the old terminal, checks retry bytes/tasks, budget quiescence and authoritative identity, emits all frame records, then advances the operation ID. Each mode also drops the reader and joins relay workers before the next mode.
3. Every old request is paired in this complete serial stream with the corresponding exact-key/exact-peer/exact-lane server retirement. The immediately preceding line must be that key's WR poll failure; its preceding request-detail record must belong to the same operation. All 1,660 pairings use unique server terminal lines and unique exact-peer connection-open lines. Server timestamps are used for nondecreasing order and coarse suite containment only; no cross-host duration is subtracted. QPN, rkey, or source-port numbers are never treated as globally unique identities.
4. For each reused peer, the previous old terminal is strictly before the next recorded connection open. For example, key `native-recovery-2026102934-0`, peer `10.81.1.2:54070`, belongs to op 118 at open/failure/retirement lines **4940 / 4950 / 4951**, and op 852 at **13101 / 13114 / 13115**. Thus these are two separate connection lifetimes, not one event counted twice. All 12 repeated key/peer groups satisfy this stronger interval check.
5. The complete formal server stream contains exactly **9,508** request-detail records and **1,660** old terminals. The small fixture has 9,496 details / 1,656 old terminals and the large fixture 12 / 4. There are zero foreign-key request details inside either formal stream and zero additional old terminals through the sealed cutoffs. Suite request groups occur in the frozen order, and the seven native process intervals do not overlap. This establishes isolation of the recorded fixture request stream; it does not assert that every unrelated host process was absent.

The replay performs **4,986 in-memory negative mutations**, preserving raw evidence: delete each terminal (1,660), duplicate each terminal (1,660), swap every adjacent terminal within each nonempty suite (1,654), and swap each of the 12 repeated same-key/peer occurrences.
