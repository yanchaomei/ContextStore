# One Worker, two rails, one complete object

The object stays in its existing disk stripes. A single Worker reads those stripes through two independently controlled RDMA paths and exposes the result only after every required byte, checksum and object-version check succeeds.

The [October 16 V4 submission materials](../kv-service/verification/results/competition-demo-20261016-v4/) include a 29-page technical report with eight figures, a 4:30 neural female narrated walkthrough, a presenter guide, independently reviewed mechanism diagrams, and a reusable competition-submission skill. The underlying [real RXE terminal capture](../kv-service/verification/results/competition-demo-20261016-v2/) and frozen safety evidence remain separately traceable.

## 1. Conflict

Concurrent disks can supply a large KV-cache object faster than one network path can carry it. Splitting the transfer across connections is tempting, but direct writes into the caller's buffer make a partial result visible. A timed-out RDMA WRITE or late CQE can outlive the request that owns its destination or source memory.

## 2. Insight

The placement already describes the object's physical stripes and owning storage endpoint. It does not require a new disk layout to select a network path. The server can optionally advertise additional fabric/listener capabilities in `LookupObject`; the client matches these to locally configured Verbs devices, assigns whole stripes by weighted bytes, and receives each rail into private registered memory. Older servers remain usable through explicit route mapping. The caller's buffer remains untouched until the full object is validated.

## 3. Mechanism

`KvClient::read_multi_rail_into` performs lookup and placement validation, asks one shared `RailReader` to plan and transfer the stripes, checks completeness and optional per-stripe xxh3, repeats the lookup to compare descriptor and placement identity, then copies the complete object under the cancellation gate. Each rail owns its QP, CQ and MR. Resource reservations cover both concurrent requests and individual rails. An uncertain WRITE completion retires the connection while its source remains pinned until QP destruction. The research branch's opt-in direct mode gives eligible Rails disjoint slices of one private ordered vector, eliminating a packed-to-ordered assembly pass while keeping the same caller publication gate. One configured rail follows the same API and remains supported.

The transport state machine is deterministic. An LLM or agent is not placed on the latency-sensitive data path because scheduling, bounds and memory ownership need explicit, testable rules. A future operator agent could diagnose metrics or suggest placement changes without controlling the safety path.

## 4. Evidence

- [Independent draft PR #32](https://github.com/DaoCloud/ContextStore/pull/32) starts from official `main`, keeps the existing object layout, and contains the implementation, tests and reusable deployment scripts.
- Two isolated KVM guests with two separate tap/bridge/RXE paths completed a 64 MiB / 16-stripe object read over real Verbs; each rail carried 32 MiB. The [four-minute demo and raw live command record](https://github.com/yanchaomei/ContextStore/releases/tag/multi-rail-softroce-demo-2026-10-02) show link shutdown/recovery, corruption/recovery and late second-rail completion.
- The first [ten-block software-RoCE evaluation](paper/evaluation-results.md) showed modest apparent two-Rail gains, but its one-Rail path copied a complete object needlessly. After a safe one-Rail handoff, the [repeated matrix](paper/baseline-ablation-results.md) found 0.904× dual/single throughput at 64 MiB/concurrency 1 (all ten blocks favor one Rail); the other three cells' intervals cross parity. This is a baseline-sensitive negative result on two KVM guests sharing one host and virtual disk.
- A separate [single-Rail physical HCA code-revision ablation](paper/baseline-ablation-results.md) confirms the copy cost: removing it improved the same 64 MiB read by 1.426× across ten paired blocks and reduced CPU/RSS. A link-capacity calibration reaches 97.94 Gb/s, so the measured application load is not demonstrated to be NIC-limited. There is no physical dual-HCA aggregation measurement.
- The [same-scheduler five-arm RXE experiment](paper/direct-staging-eval-2026-10-09.md) finds 1.100× (64 MiB) and 1.161× (256 MiB) direct/packed-contiguous throughput in the final ten-block matrices, with lower CPU/RSS and the same per-Rail registered/in-flight bytes. A second normal-path session preserves the primary benefit but weakens the 64 MiB one-Rail comparison. The 256 MiB request uses a different server source fallback.
- The [bounded safety explorer](paper/safety-model-plan.md) checks 19,657 abstract states and six weakened-guard counterexamples after independent review. Final-binary direct RXE fault receipts and a test-only QP/MR error-return injection cover normal late-WRITE/cancel behavior and the fail-stop branch. This remains an assumption-bounded safety argument, not a provider or implementation proof.
- The strongest [unique-Generation RXE campaign](paper/rewrite-race-and-server-failstop-2026-10-09.md) committed 30 distinct-content versions and timestamped 40 direct two-Rail attempts: **31 intersected an SDK PUT call after payload preparation**, of which six returned bytes matching the SDK's accepted Generation and 25 rejected without changing the caller sentinel. Server commit overlap is not established. The exact test binary is linked to 20 Git-committed source files by a Linux build receipt. Earlier unique-content runs with 51 broader PUT-plus-Lookup intersections and repeated A/B-byte runs remain labeled as weaker evidence. Test-only service-side QP/MR error-return injections aborted with launch-time binary manifests; a restarted normal service read the object again.
- A separate [Generation-transition witness](paper/generation-transition-witness-2026-10-12.md) adds eight real reads whose two metadata lookups saw a strictly newer Generation after private-staged transfer; all eight rejected while preserving the caller buffer. The single-run result is source-snapshot and binary-bound and independently re-audited. It establishes a metadata transition during each read method under the one-writer setup, without timestamping the precise server commit or RDMA WRITE state.

## 5. Next decision

Maintainer review should settle the optional capability map, direct-staging guardrails and checksum migration. A top-venue performance claim still needs two independent physical HCA paths, an actually network-limited one-Rail workload, a two-QP/one-HCA control, and matched HCA, disk, CPU, NUMA/PCIe counters under the same object and concurrency. Those results decide whether the next bottleneck is network, disk, memory or software overhead. Until then the strongest story is **one complete version, one private publication point, and less software memory movement**.

**Evidence boundary:** Two RXE rails share one host and one virtual disk. They prove real Verbs scheduling and safety behavior, not HCA offload, separate NVMe bandwidth or physical multi-NIC aggregation. Community approval, official CI execution and competition submission are separate gates.
