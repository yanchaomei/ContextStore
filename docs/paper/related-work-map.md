# Primary-source related-work map

This map is a novelty boundary for a possible ContextStore systems paper, not a claim that the cited systems have identical workloads or failure contracts. Updated 2026-10-09 after checking the [FAST/NSDI/SIGCOMM/ATC methods audit](top-venue-methods.md). Read the full papers and current code before writing a formal Related Work section.

| Primary source | What it already covers | Consequence for this work |
| --- | --- | --- |
| [UCX FAQ / UCP documentation](https://github.com/openucx/ucx/blob/master/docs/source/faq.md) | Transport selection, fragmentation and multi-rail communication across network devices. | “Multiple RDMA Rails” and device selection are established building blocks, not a standalone novel contribution. UCX does not by itself specify this store's object Generation/ETag/stripe publication contract. |
| [Feng Ren et al., *TENT: A Declarative Slice Spraying Engine for Performant and Resilient Data Movement in Disaggregated LLM Serving*, arXiv:2604.00368 (2026)](https://arxiv.org/abs/2604.00368) | Data-movement intents, automated topology/capability handling, telemetry-driven slice spraying and fault rerouting; evaluates on H800 clusters. | Direct and stronger prior art for LLM multi-rail scheduling. ContextStore's static weighted stripe assignment cannot claim scheduling superiority without a fair implementation and measurement. Its possible distinction is storage-object identity, validation and fail-stop memory ownership, which still needs novelty and invariant proof. |
| [Ruoyu Qin et al., *MOONCAKE: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot*, FAST 2025](https://www.usenix.org/system/files/fast25-qin.pdf) | §3.2.3 already slices one transfer at 16 KB granularity across multiple RDMA NICs, chooses local/remote paths with a topology matrix, pools endpoints and reroutes after connection failure. §5.4 reports physical 4×200 Gb/s and 8×400 Gb/s transfer measurements. | This is direct prior art for single-transfer multi-NIC KV-cache movement, topology selection, pooling and failure rerouting. Our candidate distinction is a specified and checked versioned striped-object read contract, failure-atomic caller publication and late-WRITE buffer retirement. The paper does not specify those exact properties, which does **not** imply its implementation lacks them. Compare contracts precisely; do not claim multi-NIC or zero-copy transfer as new. |
| [NVIDIA NIXL architecture and backend selection](https://docs.nvidia.com/nixl/getting-started/architecture/) | Memory registration metadata exchange, transfer agents and backend selection, including UCX/RDMA. | Capability metadata and backend choice are not new by themselves. Compare integration scope and lifecycle guarantees rather than branding endpoint advertisement as a new abstraction. |
| [RFC 5042, *DDP/RDMAP Security*](https://datatracker.ietf.org/doc/rfc5042/) | Remote placement and memory-key reuse/overrun risks in RDMA security. | Late-write safety is a known class of risk; the paper must show a concrete invariant and implementation/verification contribution, not claim to discover the risk. |
| [*Synchronizing Disaggregated Data Structures with One-Sided RDMA: Pitfalls, Experiments and Design Guidelines*, ACM TODS DOI:10.1145/3716377](https://doi.org/10.1145/3716377) | Explicitly discusses reuse of a source buffer while an asynchronous RDMA write remains outstanding. | Pinning the source until completion is an established principle. The contribution, if any, is how to compose that principle with multi-Rail object versioning, cancellation, CQ retirement and bounded staging in a real KV-cache store. |

## Working differentiation hypothesis

The most defensible paper question is whether a **striped, versioned remote object** can offer failure-atomic reads and safe caller-buffer reuse across multiple independently failing RDMA paths without changing the stored layout or upper read interface, and at what cost. This is narrower than TENT's dynamic transfer engine. It becomes a contribution only if: (1) the failure/version state machine is specified and checked beyond a few injected cases, (2) the measured cost of safety is separated from QP/MR/control overhead, and (3) a physical network-limited workload is established before claiming bandwidth gains.

**No paper claim yet:** no broad novelty assertion, no physical two-HCA scaling result, and no proof of a universal late-write guarantee under process crash or unspecified NIC behavior. A lower-copy multi-Rail path is an engineering experiment, not by itself a novelty claim in view of Mooncake's published zero-copy multi-NIC engine.
