# What comparable systems papers actually prove

**Literature audit:** 2026-10-09. This is a method and novelty audit for the ContextStore research branch, based on published conference papers or an author-hosted copy of the published paper. It is not a claim that these systems implement the same striped-object API. “Not specified” below means that the cited *paper* does not establish the stated contract; it is not evidence that its implementation lacks one. Our own results and gaps are recorded in [claim-evidence.md](claim-evidence.md) and [manuscript-draft.md](manuscript-draft.md).

## The hard prior-art boundary: Mooncake already does single-transfer multi-NIC slicing

[**MOONCAKE: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot**](https://www.usenix.org/system/files/fast25-qin.pdf), Ruoyu Qin, Zheming Li, Weiran He, Jialei Cui, Feng Ren, Mingxing Zhang, Yongwei Wu, Weimin Zheng, and Xinran Xu, **FAST 2025**, is the closest published systems paper. Its §3.2.3 explicitly describes an engine that distributes transfer tasks across multiple RDMA NICs, builds local and remote NIC preference lists from a topology matrix, slices a *single transfer* at 16 KB granularity so slices can use different paths, pools endpoints (each with one or more QPs), caps active connections, and finds another path and resubmits when a NIC connection fails (paper pp. 159–160). Its §5.4 compares the transfer engine with TCP and Gloo on **4 × 200 Gb/s** and **8 × 400 Gb/s** NIC configurations; it reports 87 and 190 GB/s for a 40 GB transfer, respectively, and also varies modeled network bandwidth to connect transfer cost to TTFT (pp. 165–166). Its §5.1 records a physical 4 × 200 Gb/s A800 testbed and vLLM feature baselines (p. 162).

The paper also says accessed cache blocks are protected from eviction while a request is active and offers asynchronous transfer-status polling (§3.2.1–3.2.2, p. 159). These statements **do not by themselves establish** the precise ContextStore contract: one Generation/ETag/Layout Version across disk stripes; exact nonoverlapping stripe coverage and checksum validation; all-or-nothing publication into a caller buffer; and a proof that every failed or cancelled RDMA WRITE has ceased before its target or source is deregistered or reused. I did not find that contract, a late-WRITE buffer-reuse test, or a CQ/QP lifetime proof in the published paper. This is a distinction in what the papers specify, **not** an assertion that Mooncake's code is unsafe. Its published transfer experiment also does not isolate an otherwise-identical **1 versus 2 versus 4 NIC** ablation; the 4-NIC and 8-NIC environments differ. We should not claim to invent multi-NIC slicing, topology-aware local/remote NIC choice, endpoint pooling, or failure rerouting. Our possible contribution must be the *specified and checked object-read contract* in ContextStore, or a genuinely new mechanism with a fair direct comparison.

## Implications for the current ContextStore draft

### 1. Reframe the research question

The present strongest defensible question is: **What contract and cost are required to return exactly one complete version of a striped object through independently failing RDMA paths while allowing safe reuse of caller-visible memory?** The already demonstrated 16 KB multi-NIC slicing in Mooncake makes “first multi-Rail KV-cache transfer” untenable. A sharper distinction is ContextStore's preserved disk stripe layout, Generation/ETag/Layout Version identity, exact stripe coverage, fail-stop publication and WR/CQE/MR/QP retirement. Even that is a *candidate* distinction: Pilaf already checks remote read races, Hydra already designs for multi-source failure, and the novelty claim needs a precise comparison of invariants and a systematic test/model, not just a different workload name.

The physical bandwidth story needs its own gate. The current 100 Gb/s HCA application read is far below an independent perftest bound. After correcting the one-Rail copy, the **packed** dual-RXE path lost to one Rail at 64 MiB/concurrency 1. A subsequent [same-plan direct-staging ablation](direct-staging-eval-2026-10-09.md) recovers a bounded **software-RXE** benefit at 64 and 256 MiB, but it still does not establish a physical aggregate-NIC speedup. Both the negative baseline correction and the positive direct-staging result matter to the paper story.

### 2. Build the strongest simple baseline first

**B0: optimized one-Rail ContextStore, same public read API and object.** Use the existing no-extra-assembly receive-vector handoff; preserve the same checksum, pre/post metadata lookup, staging, caller publication, slab/disk source, QP/MR connection policy and concurrency/byte caps as the multi-Rail version. Reuse or pre-establish connections symmetrically when evaluating a warm steady state; measure cold setup separately. This is the primary one-Rail comparator.

**B1: two QPs on one physical NIC**, with the same two-worker stripe assignment and safety path, separates extra QP/thread/registration parallelism from independent-NIC capacity. **B2: two independent NICs**, same object/layout, client/server and request concurrency, differs from B1 only in physical path count and affinity. **B3: lower-copy two-Rail ordered private staging** now receives into disjoint object offsets inside a private buffer and retains the failure-atomic publication. Its RXE same-plan packed control isolates a *net software staging effect*, including changed allocation and MR costs; it does not isolate pure memory-copy time or prove physical B2. These are controls, not alternative products. If B1 equals B2 and the one NIC is unsaturated, do not attribute any gain to network aggregation. Report the pre-fix one-Rail path only as a historical negative control, never the headline baseline.

If a Mooncake transfer-engine comparison is feasible through a faithful stand-alone buffer transfer, report it as a **transport-only** comparator with both implementations' registration, path setup, data size and buffer placement specified. It cannot by itself replace the ContextStore end-to-end object baseline because it does not execute the same disk/layout/version/caller-publication contract as published. Do not claim a Mooncake end-to-end performance win without implementing that contract on both sides.

### 3. Figures and tables that would make a paper testable

1. **Problem/roofline figure:** measured disk/slab supply, one-NIC perftest and ContextStore payload rate on the *same host setup*, plus control/CPU/memory-copy times; show where a second NIC could matter. Never infer a speedup by dividing two different workloads.
2. **Mechanism/state figure:** descriptor snapshot → rail assignment → private registered regions → CQ/QP retirement → coverage/checksum/version gate → one caller-buffer publication point. Show cancel and late-WRITE lifetimes, plus a compact invariant table.
3. **Topology and isolation table:** each local/remote HCA/port/GID, PCIe root, NUMA, CPU affinity, link rate and per-port counters; prove both Rails are independently discoverable, faultable and carrying bytes. Report the same for RXE with its software classification.
4. **Fixed-system 1/2-Rail scaling:** B0/B1/B2 under increasing object size and read concurrency with identical layout/source/cache state; report payload GiB/s, p50/p95/p99 object latency, per-port Gb/s and disk/slab bandwidth. Use repeated independent alternating blocks and show every block or uncertainty interval.
5. **Cost waterfall and resource budget:** pre/post lookup, QP/connect, MR registration, server read, GET/CQ, assembly, checksum and caller publication; client/server CPU, registered MiB, peak RSS, in-flight bytes and QD. Place B0/B2/B3 side by side.
6. **Correctness/fault matrix:** concurrent object rewrite, mismatched placement, missing/duplicate/out-of-range/corrupt stripe, disconnect/timeout at each Rail, cancellation and late CQE/WRITE. Include the final caller-buffer sentinel/hash, error code, QP/MR lifetime trace and time to reclamation. Report faults as counts over independent runs, not a single screenshot.
7. **Limits plot:** tune total and per-Rail queue depth, registrations and in-flight byte budgets under offered load; report throughput, p99 latency, backpressure decisions, CPU and memory, so a performance gain is not purchased with unbounded resources.

### 4. Decision gate before writing a stronger abstract

To claim **physical multi-Rail bandwidth aggregation**, acquire two independent hardware paths *and* a source workload that saturates one path; show B2>B1 and B0 with both port counters and unchanged disk/slab supply. To claim **a publishable safety mechanism**, specify the state machine and provider assumptions, explore interleavings (including cancel versus publish and timeout versus late WRITE), prove or model-check the no-reuse-before-retirement invariant, and test the actual Verbs path under controlled faults. To claim **a practical end-to-end benefit**, show a fair B0/B2 comparison after copy removal with total latency, CPU and memory, not merely a native network microbenchmark. Until then, present the current code as an independently reproducible implementation with a carefully bounded negative performance result.
