# Direct ordered staging: controlled software-Verbs evaluation

**Status:** final research-branch evidence, 2026-10-09. This is an opt-in ContextStore Rust SDK implementation on two isolated RXE paths, **not** evidence of physical multi-HCA aggregation or a claim that multi-NIC/zero-copy transfer is new. [Mooncake FAST '25](https://www.usenix.org/system/files/fast25-qin.pdf) already provides direct prior art for those broader ideas. The upstream [draft PR #32](https://github.com/DaoCloud/ContextStore/pull/32) remains a separate, earlier independent implementation; this branch's direct-staging code and paper data have not been accepted or merged upstream.

## Mechanism and comparison

The direct path leaves the stored stripe layout and public `read_multi_rail_into` API unchanged. When every stripe belongs to one nonempty storage owner and multiple local paths are eligible, it partitions consecutive stripe runs by route weight. Each scoped Rail worker borrows a disjoint mutable slice of **one request-private ordered staging vector**, registers that slice plus a separate dummy-stripe MR, and issues the existing stripe-subset SGE GET. All workers join before checksums, second object lookup and final caller-buffer publication. Other placement shapes fall back to packed mode. Both new toggles default off. A failure leaves the caller buffer untouched; QP and MR teardown errors fail-stop before memory can be recycled. Figure [packed versus direct](figures/direct-vs-packed-2026-10-09-v1/contextstore-direct-vs-packed_en.svg) shows the memory movement and ownership boundary.

The five arms are: optimized one Rail through `rxe_c0`; optimized one Rail through `rxe_c1`; original greedy/interleaved two-Rail packed mode; **packed-contiguous** mode using the direct planner's exact stripe sets but retaining assembly; and direct-contiguous mode. The **predeclared primary** contrast is direct versus packed-contiguous. It estimates the net direct-staging implementation effect while holding stripe scheduling constant; different allocation, target/dummy MR registration and teardown remain part of that effect. Total latency is not a pure `memcpy` measurement. Both one-Rail paths are reported independently; choosing the faster observed path after the fact would bias a headline ratio.

## Environment, identity and audit

The Worker and server used separate four-vCPU, 4 GiB Ubuntu KVM guests on one SKV host. Two virtio NIC pairs and separate Linux bridges carry `rxe_c0↔rxe_s0` and `rxe_c1↔rxe_s1`; [live guest and host topology](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/topology-client-v3.txt) identifies the paths as **virtual RXE**, not PCIe HCAs. Both stripe directories share one server virtual disk. The server's RDMA slab override was 128 MiB. The 64 MiB object has 16 × 4 MiB stripes and xxh3 `a0a4cbfa5cad46af`; the 256 MiB object has 64 × 4 MiB stripes and xxh3 `fe51c755b1336171`. The 256 MiB request exceeds the slab and the [server log](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/server-v3-full.log.gz) records the registered-buffer fallback. **The two sizes therefore have different source conditions**; only within-size arm comparisons share the same object and server conditions.

The final measured client binary SHA-256 is `4b511dfa061afb1131da39daac85e1d60f98b971b4f38b952e023d67865f0ee0`; server SHA-256 is `2d396c136846b3e8e4c2378c126bb2a89d148061bd220ecff6d03cac93c233d2`. Each of the ten independently launched blocks contains all five arms. Five cyclic orders plus their reverses put each arm twice in every position. Each arm performs one warmup and five measured complete-object reads. [The collector](../../kv-service/benchmarks/collect_rail_modes.py) captures exact descriptor/placement fingerprints before and after the process, whole-object hash, **effective** mode counters, per-Rail stripe indices and byte attribution, CPU and RSS. [The independent raw-log auditor](../../kv-service/benchmarks/audit_rail_modes.py) recomputes all process medians, verifies plan equality for direct versus packed-contiguous, exact object/byte coverage, per-Rail resource counters returning to zero and block order. It then forms paired log throughput ratios. The 95% percentile intervals use 20,000 seeded resamples of the **ten process blocks**, not fifty reads within processes. They describe this one VM-host setup and do not correct the secondary contrasts for multiplicity.

## Safety receipts and limits

The final binary restored the 64 MiB object with 32 MiB per RXE Rail and matching whole-object hash. Real-Verbs tests on that binary passed in-flight cancellation, a dead second listener and a delayed second-Rail WRITE after Rail 0 completes; each kept the reused caller-buffer sentinel intact. The server [fault log](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/faults/server-v3-faults.log.gz) records the 3 s injected delay, 2 s CQ deadline, `0/32` final completions and connection retirement. The test-only [cleanup return-value injection](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/failstop-injection/result.json) forced `ibv_destroy_qp` and `ibv_dereg_mr` to return errors in separate single-Rail RXE processes with stderr closed. Both terminated with `SIGABRT` before subsequent MR/buffer release; a normal read succeeded afterward. This exercises the fail-stop code branch, **not** a genuine provider failure. The [revised abstract explorer](../../kv-service/verification/results/state-explorer-revised-20261009.json) exhausted 19,657 states under explicit assumptions and found six weakened-guard counterexamples; it is not a Rust/Verbs proof.

A fresh [read-only inventory of all seven SKV nodes](physical-hca-availability-2026-10-09.md) found two enumerated Verbs devices per node but only one `ACTIVE/LINK_UP` physical port on each. We have no same-NIC two-QP control, dual-HCA port counters, verified one-NIC application saturation or fixed-source physical two-HCA comparison. RXE guests share host CPUs and one virtual disk, and this evaluation lacks matched OS link, disk-source and IRQ counters for each block. The separate `rdma-ffi`/Python external-buffer API is outside the Rust multi-Rail safety argument. These gaps prevent a claim of physical NIC aggregation, universal data-integrity detection without checksums, or implementation-level formal correctness.
