# Paper brief: failure-atomic multi-rail reads for versioned KV-cache objects

**Status:** evidence-bounded research framing, not a submission-ready paper. **Public baseline:** independent ContextStore draft PR #32 at `c1c1de1`. **Research branch:** `research/direct-ordered-staging` contains opt-in direct mode, reviewed abstract model and final five-arm RXE data. Physical single-HCA and two-Rail Soft-RoCE evidence have distinct boundaries.

## One-sentence thesis

An object store can exploit independent RDMA paths for one striped KV-cache object while preserving an all-or-nothing, single-version read, if each Rail writes only into request-owned registered staging memory and a request cannot publish or reclaim that memory until the transport and version checks settle.

## Why this is a systems problem

The stored object already has a stripe layout, owner placement, Generation, ETag and Layout Version. A network scheduler can assign those stripes to different Rails without moving them. The hard part is the boundary between partial asynchronous WRITEs and caller-visible object state: a failed or cancelled Rail may still have a posted WRITE, a CQE may arrive after timeout, and another request may reuse the destination or a server-side source. A correct read must treat path selection, completion, object identity and memory reclamation as one state machine.

## Mechanism chain

1. **Owner-bound discovery and routing:** optional Placement capabilities bind an actual stripe owner and primary endpoint to reachable fabric/listener pairs. Local device/port/GID configuration supplies the other half. Owner, listener and route-count checks reject ambiguous paths before data transfer. This is integration and safety context, not claimed as new topology scheduling.
2. **Private multi-Rail transfer:** weighted whole-stripe planning reuses the disk layout and tag-15 SGE path. The default receives into compact per-Rail targets; opt-in direct mode gives eligible single-owner objects consecutive stripe runs and disjoint mutable slices of one private ordered vector. A packed-contiguous control keeps exactly that assignment while retaining assembly. Each Rail has its QP/CQ/MR; a shared budget caps staging, registration and in-flight bytes. The server validates descriptor identity and requested stripe ranges.
3. **Failure-atomic completion:** the reader joins all started tasks, verifies exact byte/stripe coverage and optional checksums, performs a second `LookupObject`, compares descriptor plus Placement, and copies the complete object under the cancellation gate. Transport errors, stale versions and incomplete data leave the caller buffer untouched.
4. **Safe retirement:** client control errors destroy the QP before releasing its target MR. Server-side uncertain WRITEs retain slab extents, cache pins or `(MR, Bytes)` sources until QP destruction; a connection with uncertain CQ state is not reused. Direct staging adds an independent ownership rule: the one ordered vector remains private until publication or failure, even after DMA quiesces. Failed provider QP/MR teardown causes fail-stop rather than recycling memory. This contract covers the Rust SDK path, not the separate Python/FFI external-buffer API.

## Evidence already measured

- Two isolated RXE Rails restored a 64 MiB / 16-stripe object, 32 MiB per Rail; link shutdown, timeout, checksum/version failure, cancellation and late-WRITE controls returned whole-object failure and preserved a reused buffer in the injected traces. Server/client release suites and isolated two-node E2E pass. These are **correctness checks**, not a formal proof.
- The first [ten-block Soft-RoCE matrix](evaluation-results.md) showed apparent two/one-Rail gains of 1.038–1.101×, but its one-Rail path needlessly copied the entire completed object. After a safe handoff fast path, the [repeated matrix](baseline-ablation-results.md) yields 0.904× at 64 MiB/c1 (all ten blocks favor one Rail), 0.958× at 256 MiB/c1, 0.991× at 64 MiB/c4 and 1.037× at 256 MiB/c2; the last three intervals cross parity. [Every new block](figures/rxe-fastbaseline-ten-blocks.svg) and the historical matrix are retained. These are software RXE results on two guests sharing one host and one virtual disk, not physical multi-HCA evidence.
- Three physical single-HCA `ib_write_bw` calibrations achieved 97.96/97.85/97.94 Gb/s. The original [stage pilot](stage-trace-pilot.md) attributed 53.2 ms of a 64 MiB read to an avoidable assembly copy. A same-object, same-server [ten-block code-revision ablation](baseline-ablation-results.md) removed it, improving single-HCA one-Rail latency by a 1.426× paired geometric mean (95% block interval 1.342–1.534×) and cutting CPU/RSS. The NIC is still not demonstrated to be the limiting resource.
- The [final five-arm RXE matrix](direct-staging-eval-2026-10-09.md) holds stripe assignment constant and gives direct/packed-contiguous 1.100× throughput for 64 MiB and 1.161× for 256 MiB, with lower CPU/RSS and the same registered/in-flight payload. A second near-identical session preserves the primary same-plan benefit; its 64 MiB direct/one-Rail interval crosses 1, limiting the single-Rail claim. The 256 MiB object uses a server fallback because it exceeds the 128 MiB slab.
- Final direct-mode RXE cancellation, dead-listener and late-WRITE tests preserve a caller-buffer sentinel. A test-only return-value shim exercises fail-stop with stderr closed; a [bounded two-Rail model](safety-model-plan.md) exhausts 19,657 states and gives six negative traces under explicit assumptions. These are neither a provider failure experiment nor a proof of the Rust/Verbs implementation.
- A [unique-Generation SDK-call campaign](rewrite-race-and-server-failstop-2026-10-09.md) gives every committed overwrite different bytes, records the SDK's accepted Generation and separates PUT return from post-PUT Lookup. Among 40 attempts, **31 intersected an SDK PUT call after payload preparation**: six returned one complete accepted Generation and 25 safely rejected. Server commit overlap remains unknown. A build receipt matched 20 source files to the code commit and the launch-time binary hash. Earlier preparation-inclusive runs had 36 broader intersections, and still earlier runs supplied 51 PUT-plus-Lookup intersections; the 75-write/100-attempt A/B campaign is historical pattern/sentinel evidence. Test-only **server** QP/MR aborts carry launch-time server/shim/script/client hashes plus a successful restart. None is a provider-level fault or code-to-model proof.
- A separate [single-process Generation-transition witness](generation-transition-witness-2026-10-12.md) observed eight reads whose pre/post-transfer metadata lookups returned strictly increasing Generations. All eight safely rejected with the caller sentinel unchanged. This supports a metadata transition during each read method under the single-writer/no-delete setup; it does not timestamp the server commit or show that an RDMA WRITE was in flight at that instant.

## Novelty and claim boundary

[UCX](https://github.com/openucx/ucx/blob/master/docs/source/faq.md) already supports multi-rail transfer. More directly, [Mooncake's FAST '25 paper](https://www.usenix.org/system/files/fast25-qin.pdf) already slices one transfer across multiple RDMA NICs, selects local/remote paths by topology, pools endpoints, reroutes failures, and measures physical multi-NIC bandwidth. [TENT](https://arxiv.org/abs/2604.00368) applies telemetry-driven slice scheduling to disaggregated LLM serving and is stronger than this static scheduler on that axis. [NIXL](https://docs.nvidia.com/nixl/getting-started/architecture/) covers transfer capabilities; RDMA memory-key/buffer lifetime hazards are established in [RFC 5042](https://datatracker.ietf.org/doc/rfc5042/) and later design-guideline work. This project should **not** claim “first multi-rail KV-cache transfer,” “novel static striping,” “automatic topology optimization,” “new zero-copy multi-NIC transfer,” or physical bandwidth aggregation. See the [formal-venue methods audit](top-venue-methods.md).

The plausible research contribution is an **object-level failure and version contract** composed with multi-Rail RDMA, plus an experimentally isolated way to reduce **multi-Rail software staging** cost safely. The one-Rail baseline correction is a controlled ablation, not a new algorithm. The bounded state explorer and direct path now exist, but a code-to-model refinement proof and an actual network-limited physical workload are still missing. Until those gates pass, describe the work as a rigorous open-source artifact and software-Verbs safety/cost study rather than a hardware aggregation paper.

## Provisional abstract (evidence-bounded)

> A striped KV-cache object read across independently failing RDMA paths must preserve one version and an unchanged caller buffer until every required byte is verified. We implement this contract in ContextStore's Rust SDK and KVService without changing the stored stripe layout or public read API. A direct multi-Rail mode receives into disjoint slices of one request-private ordered vector; both normal and fault paths retire QPs before MR/buffer reuse, and the final caller copy follows a version/checksum gate. Real two-path Soft-RoCE fault injection preserves caller sentinels, while a bounded two-Rail model checks 19,657 abstract states under explicit provider assumptions. Correcting an avoidable one-Rail copy improved physical single-HCA read latency 1.426× and exposed a misleading older software-RXE dual-Rail comparison. Against a same-scheduler packed control, direct staging improves RXE throughput 1.100× at 64 MiB and 1.161× at 256 MiB in ten balanced blocks per object, with lower CPU/RSS and unchanged registered payload. The physical application is not shown NIC-limited, and no dual-HCA aggregation claim follows.

## Suggested paper organization

1. Workload and problem: object stripes, version identity, asynchronous WRITE lifetimes; demonstrate the actual bottleneck rather than assuming it.
2. Contract and state machine: atomic visibility, version identity and QP/MR lifetime invariants.
3. Design and implementation: owner-bound discovery, weighted assignment, private targets, checks and retirement.
4. Cost model and stage accounting: lookup, QP/MR, server I/O, wire, assembly, checksum and publish.
5. Evaluation: controlled 1/2-Rail hardware and RXE settings, fault matrix, overhead ablations and failure cases.
6. Related work and limits: TENT/UCX/Mooncake/NIXL, existing RDMA safety principles, no transparent same-request retry.
