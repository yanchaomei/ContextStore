# ContextStore 多轨读取：研究摘要与验收边界

**最近证据更新：** 2026-10-12。

**建议题目：** 面向版本化 KV Cache 对象的故障原子多轨 RDMA 读取：ContextStore 的安全机制与软件路径成本研究

**一句话故事：** 一个 Worker、两条可独立故障的 RDMA 路径、一个完整版本；数据先进入请求私有内存，经全部 Rail 和版本校验后才一次性发布给调用方。

## 问题与方法

ContextStore 的大对象已有磁盘条带，网络路径选择无需改写存储布局。难点是多条路径上的 RDMA WRITE、QP/CQE、MR 和调用方目标缓冲区有不同生命周期：一条 Rail 超时并不代表另一条 Rail 已停止写入。实现将条带映射到独立 Rail，收到请求私有的已注册内存，汇总完整覆盖、实际字节数及提供的校验和，再比较传输前后的对象 Handle、Generation、ETag、Layout Version 与 Placement。最终复制与取消共用发布门锁；失败时不返回不完整对象。Rust SDK 的新直接暂存模式让两个 Rail 借用同一私有有序向量中**互不重叠**的切片，省去打包缓冲区到有序向量的一次全对象组装复制。QP 销毁或 MR 注销若报告失败，Rust SDK 与服务端采用 fail-stop，防止继续复用可能被 DMA 引用的内存。

## 可核验的结果

- **功能与故障：** 两个独立虚拟链路上的 `rxe_c0/rxe_c1` 通过标准 Verbs 读取同一个 64 MiB、16 条带对象，每条 Rail 承担 32 MiB。最终二进制的取消、第二路径不可达、延迟第二 Rail WRITE 测试均保持调用方复用缓冲区哨兵。客户端 RDMA 特性单元测试 53 项、服务端 102 项通过；另有一个有意忽略的 Mock 性能测试。
- **有界安全检查：** 经独立审查修订的两 Rail 抽象状态探索器穷举 19,657 个状态；去掉晚到写入复用、共享暂存所有权、源内存保留、完整覆盖、取消/发布顺序、二次版本比较等保护，分别得到反例。它验证的是手工抽象规则，不是 Rust/Verbs 的形式化证明。测试专用 Verbs shim 在关闭 stderr 后强制 QP/MR 清理返回错误，两种情况均在后续 MR/缓冲区释放前收到 `SIGABRT`；这不是实体网卡提供者故障。
- **唯一 Generation 并发压力与服务端异常清理：** 最严格的两轮真实 RXE 运行提交 30 个**内容各不相同**的对象版本，记录 40 次读取及每次 SDK PUT 返回时刻；写端先构造 payload，再开始计时。其中 **31 次读取区间与 SDK PUT 方法调用相交**，六次逐字节返回与 SDK 接受 Generation 一致的完整内容，25 次安全拒绝且哨兵不变；服务端提交相交次数未知。Linux 构建收据将 20 份源码逐文件匹配到 Git 提交，并证明生成的二进制哈希与两次启动清单一致；另一台物理节点重算审计 JSON 完全一致。隔离服务端 QP 销毁与 MR 注销错误返回注入均以 134（SIGABRT）结束，启动清单记录服务端/shim/脚本/客户端哈希，普通服务重启后同一对象成功读回。较早两轮实验的 36 次只与“数据准备＋SDK 调用”相交；再早三轮唯一内容实验的 51 次只与“PUT＋事后 Lookup”整轮相交，**不能**等同 PUT 相交；旧 A/B 复用内容实验只能证明未观察到字节图案混合。[原始审计与限制](rewrite-race-and-server-failstop-2026-10-09.md)明确这些仍是有限调度和测试 shim 证据。
- **元数据版本切换见证：** 随后一轮真实双 RXE 测试的 20 次读取均与 SDK PUT 调用相交；其中八次拒绝记录了同一读取初查与复查的 Generation 严格增长，另外两次为 Descriptor stale，十次完整接受。八次版本切换拒绝都保持调用方缓冲区哨兵。单写端、无删除、递增 Generation 和原子元数据替换使这八组初查/复查成为“读方法执行期间发生元数据提交”的直接见证；提交精确时间及 RDMA WRITE 是否在途仍未知。该轮源码快照、二进制与另一物理节点独立重算结果见[补充材料](generation-transition-witness-2026-10-12.md)，不与前述两轮计数合并。
- **受控性能：** 64/256 MiB 每个对象运行十个五组平衡进程块；组别是两条单轨、原打包调度、与直接暂存**条带分配完全相同**的打包对照，以及直接暂存。最终二进制直接/同分配打包的吞吐几何平均比为 **1.100×**（64 MiB，95% 块重采样区间 1.048–1.161×）和 **1.161×**（256 MiB，1.117–1.209×）。双轨注册内存和在途字节并未减少，客户端峰值 RSS 分别约由 206.3→142.5 MiB、782.5→526.6 MiB。每次完整读取摊销的进程 CPU 分别约由 123.9→76.5 ms、433.6→259.4 ms。早一轮近似相同正常路径的主对照仍为 1.121×/1.134×；但其 64 MiB 对较快单轨的区间跨 1，不宜宣称这一尺寸稳定胜过最强单轨。
- **先修正基线：** 原单轨路径多复制一次整个对象，曾让双轨 RXE 增益显得更好。十个物理单 HCA 配对进程块证明去掉该复制后，单轨延时改善 **1.426×**；修正后的旧打包双轨在 64 MiB、并发 1 时反而只有单轨吞吐的 **0.904×**。新直接暂存是针对这一成本的受控改进，不能把旧慢基线当成新结果的对照。

## 顶会论文式证据边界

[Mooncake（FAST 2025）](https://www.usenix.org/system/files/fast25-qin.pdf) 已明确实现单次传输跨多张 RDMA NIC 切片、拓扑感知路径和物理多网卡实验。因此本工作不能把“首个多网卡 KV Cache 传输”或“零拷贝多轨”当作新颖性。现有较窄的研究问题是：**版本化磁盘条带对象在独立失败的 RDMA 路径上，如何同时保证完整版本发布、晚到传输内存安全和可控的软件暂存成本？** [六篇顶会方法对照](top-venue-methods.md)据此要求强单轨基线、相同条带分配的机制消融、原始块级日志、故障切点和明确的硬件/软件边界。

本次两条 Rail 都是同一宿主机上两个 KVM 客户端/服务端虚拟网口对应的 **Soft-RoCE** 路径，两个服务端条带目录还共用一块虚拟磁盘。256 MiB 对象超过 128 MiB 服务端 RDMA slab，走注册缓冲区后备路径；所以 64→256 MiB 的变化同时改变了源模式。现有物理集群每节点仅观察到一条在线 HCA 路径，应用单轨也没有被证明达到 NIC 上限。**目前不能证明物理双 HCA 聚合带宽、PCIe/NUMA 收益或硬件卸载。** 独立的 Python/`rdma-ffi` 外部缓冲区 API 不在本文 Rust 多轨内存安全声明内。上游 [PR #32](https://github.com/DaoCloud/ContextStore/pull/32) 仍是较早独立实现的草稿；本研究分支的直接暂存增量尚未得到维护者评审或合入。

若要从扎实的竞赛/研究原型推进到强系统顶会性能论文，下一道不可省的门槛是：**同一对象、同一存储源和二进制下，单 HCA 一 QP、单 HCA 两 QP、双独立 HCA 三个对照；先证明一条 HCA 已饱和，再用两端口计数、磁盘读带宽、CPU/NUMA/PCIe 证据证明瓶颈确实转移。** 同时需要并发重写压力实验、真正的提供者故障和代码到状态模型的对应论证。缺这些证据时，应如实定位为可复现的软件 Verbs 安全与成本研究。
