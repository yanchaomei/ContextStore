# Experiment card: physical single-Rail stage accounting

**Question:** Why does the existing 64 MiB ContextStore HCA read take ~163 ms when a one-QP WRITE microbenchmark fills the same 100 Gb/s port at ~98 Gb/s and the server's stripe-subset diagnostic is ~16 ms?

**Status:** completed as a **pilot** on 2026-10-03. The [raw logs and audited JSON](../../kv-service/benchmarks/results/paper-hca-stage-2026-10-03/) contain two traced and two control processes, each with one warmup plus five measured reads. The [per-read stage figure](figures/physical-single-hca-stage.svg) plots all ten traced reads. The source files and client binary are SHA-pinned in `audit.json`; this is research-branch instrumentation, not the `c1c1de1` PR binary.

**Original hypothesis:** Fixed client/control costs (two metadata lookups, QP setup, MR registration, staging/checksum/publish) dominate this small object's end-to-end latency.

**System/control:** node1 server and node2 client, mlx5_1 port 1/GID 3, the same checksummed 64 MiB/16-stripe object (`xxh3=a0a4cbfa5cad46af`), same storage directories and cache policy, same one-Rail `RailReader`, one read at a time. The 128 MiB server slab was enabled and disk forcing disabled, so the reads were **warm-slab eligible**; the exact hit source was not independently proven per request. A research-only opt-in timing flag emits per-stage microseconds without changing return values. Each traced process was followed by an untraced process of the same binary; do not combine these observations with the older `1bd4821` timing samples as one statistical cell.

**Measurements:** end-to-end wall; initial/post `LookupObject`; blocking transfer; commit; within transfer: plan/reserve, QP connection, target allocation, MR registration, GET/CQ response, teardown, assemble/copy, stripe checksums. The server `RDMA_SUBSET_DETAIL` log from the same window has no shared request ID and is **not** joined to individual client reads. HCA counters were read once after the pilot, but no matched before/after delta was collected, so this pilot makes no port-utilization claim. The CLI logs include client CPU and peak RSS.

**Sanity gate:** all 10 traced reads passed a strict parser: each nested stage had nonnegative residual under 10%, and the gap between the outer stage total and CLI wall time was at most 1.66%. Each bar in the figure adds its residual as `other` and therefore closes exactly. This checks the accounting, not the accuracy of every probe.

**Observed stages:** across ten measured traced reads, the end-to-end median was 153.061 ms. Marginal stage medians were 32.220 ms target allocation/initialization, 53.182 ms object assembly copy, 19.656 ms final publication copy, 19.165 ms GET/CQ (including remote service and transfer), 12.840 ms QP connection, 7.076 ms checksums, and 1.242 ms MR registration. Marginal medians come from potentially different reads and should not be added as an exact representative timeline. The same-window server subset diagnostic median was 17.994 ms across 24 records including four warmups; it is not request-ID matched. Two traced/control process-median ratios were 1.009 and 0.981, so the observed block-to-block variation exceeds any consistent probe effect in this small pilot. Five repeated reads per process are not independent replicates.

**Interpretation:** buffer initialization, assembly and publication are substantial costs in this environment. The GET/CQ interval is a composite and cannot be labeled pure network time. The HCA link calibration is a separate microbenchmark; together these observations argue against treating the available 64 MiB workload as a demonstrated single-NIC bottleneck. They motivate a safety-preserving staging-cost ablation, but no such optimization has yet been implemented or measured.

**Failure interpretation:** if the server I/O or CQ stage dominates, investigate storage source and network saturation with matched counters; if QP/MR dominates, compare connection reuse or MR reuse as a labeled design ablation; if assembly/checksum dominates, measure memory bandwidth/CPU and do not attribute gains to NICs. If the traced binary changes latency materially, use external profiling or lower-overhead sampling.

**Reproduce:** `python3 kv-service/benchmarks/audit_hca_stage.py --logs kv-service/benchmarks/results/paper-hca-stage-2026-10-03 --output kv-service/benchmarks/results/paper-hca-stage-2026-10-03/audit.json`, then `python3 kv-service/benchmarks/plot_hca_stage.py --audit kv-service/benchmarks/results/paper-hca-stage-2026-10-03/audit.json --output-prefix docs/paper/figures/physical-single-hca-stage`. This experiment cannot establish multi-Rail HCA aggregation.
