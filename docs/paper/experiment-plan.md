# Claim-driven evaluation plan for multi-rail ContextStore

**Date:** 2026-10-03. **Status:** plan with completed link-capacity and physical single-Rail stage-accounting pilots. The two candidate contributions are (C1) failure-atomic, version-consistent striped reads across Rails and (C2, conditional) throughput aggregation only when a physical single Rail is the limiting resource. Do not turn C2 into a result without a verified link-limited workload.

## Problem and cost model

For an object of size `D` with stripe ownership fixed, an ideal dual-Rail lower bound is `max(D/B_source, D/(B_rail0+B_rail1), D/B_memory, T_cpu)`. The actual end-to-end time also includes two metadata lookups, QP establishment, MR registration, per-Rail control messages and CQ waiting, private staging, checksum validation and the final caller-buffer copy. These terms may overlap; they must be measured rather than simply summed. The useful output is a per-request stage timeline plus its total wall time, not a synthetic “network speedup” obtained by dividing the port rate by object size.

## Safety invariants

1. **Atomic visibility:** before the commit gate succeeds, the caller's destination remains unchanged; any required Rail failure returns no complete object.
2. **Version identity:** every published stripe passes length/coverage/checksum checks and belongs to the same descriptor and placement `(object_handle, generation, ETag, layout_version)` observed after transfer.
3. **Memory lifetime:** any destination or source referenced by a posted RDMA WR remains registered and un-reused until its QP is destroyed or all relevant completions are known. A late CQE cannot be consumed as a later request's success.

## Run order, units and stopping rules

1. **M0 - audit existing data (local, <1 h):** verify raw CSV counts, object hashes, block pairing, per-Rail byte conservation and source commits. Compute *paired trial-level* ratios from raw samples. Existing 3 sequential blocks and 2 concurrent blocks are descriptive; five reads in one process are repeated observations, not independent replications. Deliver a machine-readable audit and preserve the unfavorable 64 MiB/concurrency-4 block.
2. **M1 - physical single-Rail stage pilot (node1/node2): completed.** Ten traced and ten control reads from four independently launched processes are preserved with exact binary/source hashes. All traced stage sums reconcile; server diagnostics remain unpaired because neither side logs a common request ID. The initial outcome is high buffer initialization/assembly/publish cost rather than a measured wire ceiling. Next: add request IDs and matched HCA/cache counters before claiming the server or NIC is causal.
3. **M2 - RXE paired pilot: completed for a bounded four-cell matrix.** Ten AB/BA blocks each at 64/256 MiB c1, 64 MiB c4 and 256 MiB c2. Sequential arms have five measured reads after a warmup; concurrent arms have three batches after a warmup. The first arm was fixed by odd/even block parity, not randomized; this is fully disclosed. The 256 MiB c4 case was not run because the 4 GiB guest and registered-memory footprint make it a poor controlled cell. Every raw arm output and negative block is retained. Next expansion should add link/disk counters or staging ablations, not just more repetitions of the same software limit.
4. **M3 - safety interleaving (two RXE guests, ~1 h):** repeat each fault class with fixed seeds and record raw QP/MR/CQ traces, destination sentinels and next-request recovery. Add a small explicit state model; if a counterexample appears, repair the code and restart this block rather than aggregating mixed revisions.
5. **M4 - physical two-HCA experiment (resource-dependent):** run only after the topology and single-Rail saturation preflight succeeds. If two live independent HCA paths cannot be provided, write a software-Verbs paper/experience report with no hardware aggregation claim.

For paired performance, the unit is one independently launched, ordered 1/2-Rail block; compute log throughput ratios per block and report their geometric mean, range and a block-level interval when at least 10 blocks are available. Do not treat individual reads inside one process as independent trials. Report p95 only with enough raw requests to make a tail estimate meaningful; the current five-read runs are insufficient for p95 inference. Include CPU, RSS, registered bytes and in-flight bytes with every throughput result.

## Related-work and venue gate

UCX and TENT already implement multi-rail transport strategies; Mooncake and NIXL address disaggregated KV transfer. The contribution must be framed around object-level correctness/lifetime or a genuinely new, measured scheduling mechanism, not merely two RDMA connections. A systems-conference claim requires B1, B2 and B4 plus comparison against the closest mechanisms. Without B4, an artifact/experience or workshop route is more defensible; choose venue only after the evidence gate, not from CFP keywords.
