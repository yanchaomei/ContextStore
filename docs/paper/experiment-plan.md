# Claim-driven evaluation plan for multi-rail ContextStore

**Updated:** 2026-10-09 after the [six-paper formal-venue audit](top-venue-methods.md) and final direct-staging evaluation. **Status:** link-capacity, stage-accounting, ten-block one-Rail copy ablation, original/corrected RXE matrices, bounded ownership model, real-RXE fault repeat and balanced five-arm direct-staging matrices complete. The two candidate contributions are (C1) failure-atomic, version-consistent striped reads across Rails and (C2, conditional) throughput aggregation only when a physical single Rail is the limiting resource. Mooncake already demonstrates single-transfer multi-NIC slicing and physical multi-NIC bandwidth; software-RXE direct staging establishes a software-path cost result, **not** C2. Do not turn C2 into a result without a verified link-limited workload and a fair same-NIC control.

## Problem and cost model

For an object of size `D` with stripe ownership fixed, an ideal dual-Rail lower bound is `max(D/B_source, D/(B_rail0+B_rail1), D/B_memory, T_cpu)`. The actual end-to-end time also includes two metadata lookups, QP establishment, MR registration, per-Rail control messages and CQ waiting, private staging, checksum validation and the final caller-buffer copy. These terms may overlap; they must be measured rather than simply summed. The useful output is a per-request stage timeline plus its total wall time, not a synthetic “network speedup” obtained by dividing the port rate by object size.

## Safety invariants

1. **Atomic visibility:** before the commit gate succeeds, the caller's destination remains unchanged; any required Rail failure returns no complete object.
2. **Version identity:** every published stripe passes length/coverage/checksum checks and belongs to the same descriptor and placement `(object_handle, generation, ETag, layout_version)` observed after transfer.
3. **Memory lifetime:** any destination or source referenced by a posted RDMA WR remains registered and un-reused until its QP is destroyed or all relevant completions are known. A late CQE cannot be consumed as a later request's success.

## Run order, units and stopping rules

1. **M0 - audit existing data (local, <1 h):** verify raw CSV counts, object hashes, block pairing, per-Rail byte conservation and source commits. Compute *paired trial-level* ratios from raw samples. Existing 3 sequential blocks and 2 concurrent blocks are descriptive; five reads in one process are repeated observations, not independent replications. Deliver a machine-readable audit and preserve the unfavorable 64 MiB/concurrency-4 block.
2. **M1 - physical single-Rail stage pilot (node1/node2): completed.** Ten traced and ten control reads from four independently launched processes are preserved with exact binary/source hashes. All traced stage sums reconcile; server diagnostics remain unpaired because neither side logs a common request ID. The initial outcome is high buffer initialization/assembly/publish cost rather than a measured wire ceiling. Next: add request IDs and matched HCA/cache counters before claiming the server or NIC is causal.
3. **M2 - RXE paired pilot: completed twice, before and after baseline correction.** Both revisions have ten AB/BA blocks each at 64/256 MiB c1, 64 MiB c4 and 256 MiB c2. Sequential arms have five measured reads after a warmup; concurrent arms have three batches after a warmup. The first arm was fixed by odd/even block parity, not randomized; this is disclosed. The 256 MiB c4 case was not run because the 4 GiB guest and registered-memory footprint make it a poor controlled cell. Every raw arm output and negative block is retained. The corrected result removes any established software-RXE multi-Rail speedup in this setup. Next expansion should test a lower-copy multi-Rail mechanism with link/disk counters, not just repeat the original scheduler.
4. **M3 - safety interleaving: bounded slice complete, broader campaign open.** Final-binary direct RXE cancellation, dead-link and late-second-WRITE receipts preserve the sentinel; a test-only shim forces QP/MR cleanup error returns with stderr closed and confirms fail-stop plus normal next-process recovery. The [reviewed explicit-state model](safety-model-plan.md) exhausts 19,657 two-Rail abstract states and gives six weakened-guard traces. It does not model budgets, all real provider outcomes or arbitrary stripe counts. Repeat the real fault matrix with more independent timings and a concurrent writer/readers identity audit before treating this as a strong safety paper claim.
5. **M4 - physical rail-count experiment (resource-dependent):** run only after the topology and optimized one-Rail saturation preflight succeeds. Add the **two-QP/one-HCA** control before comparing with two distinct HCAs, then isolate ordered-staging cost. If two live independent HCA paths cannot be provided, write a software-Verbs paper/experience report with no hardware aggregation claim.

For paired performance, the unit is one independently launched, ordered 1/2-Rail block; compute log throughput ratios per block and report their geometric mean, range and a block-level interval when at least 10 blocks are available. Do not treat individual reads inside one process as independent trials. Report p95 only with enough raw requests to make a tail estimate meaningful; the current five-read runs are insufficient for p95 inference. Include CPU, RSS, registered bytes and in-flight bytes with every throughput result.

## Related-work and venue gate

[Mooncake FAST '25](https://www.usenix.org/system/files/fast25-qin.pdf) already implements one-transfer multi-NIC slicing, topology choice, endpoint pooling and physical multi-NIC evaluation; UCX and TENT add further prior art. The candidate distinction must be the specified versioned-object/failure-atomic lifetime contract, backed by actual Verbs fault traces and an interleaving model, not two RDMA connections or zero-copy transfer alone. A strong systems-performance paper requires B2, B4 and B5 plus a fair contract-level comparison; without B5, an artifact/experience or workshop route is more defensible. Choose venue only after the evidence gate, not from CFP keywords.
