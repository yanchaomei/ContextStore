# Failure-Atomic Multi-Rail Reads for Versioned KV-Cache Objects: A ContextStore Experience

**Manuscript status:** evidence-bounded draft, 2026-10-03. The implementation is an independent, unmerged [ContextStore draft PR #32](https://github.com/DaoCloud/ContextStore/pull/32); this research branch adds analysis and a faster one-Rail control. No maintainer acceptance, formal proof, physical dual-HCA aggregation or conference submission is implied.

## Abstract

Large KV-cache objects may already be striped across storage devices. Reading one object over several RDMA paths should preserve its version and all-or-nothing visibility even when a path times out, a WRITE arrives late, or an object is rewritten. We implemented an opt-in multi-Rail read in ContextStore that leaves the disk layout and upper read interface unchanged. The client matches owner-bound advertised endpoints to local Verbs devices, assigns whole stripes to Rail workers, receives into private registered memory, joins all workers, verifies lengths and checksums, rechecks object identity, and only then publishes the complete value. Client and server retire uncertain QPs before reclaiming the memory referenced by posted WRs. Two isolated Soft-RoCE paths reconstruct the same 64 MiB object and pass injected disconnect, cancellation, version, corruption and late-completion checks. Performance was more subtle: a physical 100 Gb/s link reached 97.94 Gb/s in a one-QP WRITE calibration, while the application's 64 MiB single-Rail read remained far below link capacity. Stage accounting exposed a redundant full-object copy in the one-Rail control. Removing it improved one-Rail latency by 1.426× across ten paired physical-HCA process blocks. With this corrected baseline, two software Rails were slower at 64 MiB/concurrency 1 (0.904× throughput, ten of ten blocks favoring one Rail), while three other workload intervals crossed parity. The experience separates multi-path correctness from throughput scaling and shows why a safe but avoidably slow one-Rail baseline can create a false multi-Rail performance story.

## 1. Introduction

KV-cache loading is an object read with several coupled identities: the bytes, the layout that names each stripe, and the version the caller expects. ContextStore can stripe a large object across devices. If storage supply exceeds one network path, independent RDMA Rails are an attractive way to aggregate bandwidth without rewriting the disk layout. Yet each Rail introduces a QP/CQ, registered target memory, a separate control exchange and an asynchronous completion history. An error on one Rail does not prove that another Rail's WRITE has stopped. Directly writing into the caller's destination would make a partially loaded object visible; freeing a timed-out target can expose a reused allocation to a delayed WRITE.

The design question is therefore broader than how to distribute stripes. A successful request needs complete coverage of one object version, a failure-atomic publication point, and safe memory retirement on both sides of the WRITE. It also needs a performance comparison that starts from the best reasonable one-Rail implementation. We built those checks inside ContextStore's Rust SDK, RDMA FFI and KVService path and measured them on real Verbs, including two independent RXE devices. The implementation keeps one-Rail deployment and older endpoint configurations available.

Three observations shape this paper. First, fault injection can exercise a useful object-level safety contract without requiring physical dual HCAs. Second, the available physical application's single HCA is **not demonstrated** to be saturated: a link-capacity microbenchmark and the application run have very different rates and very different work. Third, optimizing a redundant one-Rail copy reverses the initial software-RXE performance interpretation. A multi-Rail design can be correct and still fail to improve the tested workload.

The contributions are an integrated implementation and independently inspectable evidence rather than a claim that multi-Rail transfer is new. We provide (1) a failure-atomic, version-checked read path and its memory-lifetime argument; (2) fault and compatibility receipts on two isolated real-Verbs RXE paths; and (3) a controlled code-revision ablation and repeated one/two-Rail matrix showing how baseline construction changes the conclusion. The [claim ledger](claim-evidence.md) marks which statements are tests, measurements, hypotheses or unsupported claims.

## 2. Read contract and failure model

Let `V0` be the descriptor and placement returned before transfer and `V1` those returned after all Rail workers terminate. A published read requires identical `(object_handle, generation, ETag, layout_version, placement)` at both lookups, exact object length, a complete nonoverlapping stripe map, exact per-Rail response counts and every supplied checksum to match. The first lookup fixes a candidate snapshot; the second rejects a rewrite observed during transfer. This contract does not promise that the value remains current after the second lookup. It also assumes a new object version changes the metadata identity and that bytes of a named version are not silently mutated without a checksum failure.

Let `C` be the caller buffer, `P_r` a private registered destination for Rail `r`, `Q_r` its QP/CQ, and `S_r` a server source extent/MR. `C` is never an RDMA target. On a control timeout or uncertain completion, the client retires `Q_r` before deregistering or reusing `P_r`; the server retains `S_r` until the corresponding QP is destroyed. Every started worker joins before request-owned staging can be released. The publication copy runs only after all checks and under a mutex shared with cancellation, so cancellation and publication have one order. [The implementation-linked safety contract](safety-contract.md) states the invariants and provider assumptions precisely. It is an argument sketch, not a machine-checked proof or a claim about process-crash recovery.

The first version stages each Rail's compact receive buffer, then assembles the ordered object into a separate private vector. A later optimization moves the sole Rail's receive vector directly into staged ownership when that one task covers the complete object and each packed offset equals its object offset. The QP/MR have already retired before the vector moves; checksums, version recheck and final caller copy remain unchanged. This is a safe baseline correction, not a change to the multi-Rail path. The [design and controlled ablation](baseline-ablation-results.md) record the precondition and its measured effect.

## 3. ContextStore integration

**Path discovery.** Optional placement capabilities bind a real storage owner and advertised endpoint to fabric/listener pairs. The local configuration maps those fabrics to a Verbs device, port and GID. The reader rejects ambiguous owner/listener mappings, missing paths and unexpected placement changes before moving bytes. Manual explicit routes preserve older servers; a single configured Rail uses the same API. This capability exchange is compatibility plumbing, not a novelty claim about routing.

**Scheduling and transfer.** The planner retains the stored stripe order and layout. It assigns whole stripes among eligible Rails by weighted assigned bytes and creates a per-Rail task. Each worker owns a QP/CQ and a registered private target; the server validates descriptor identity, requested indices, owners and ranges. A shared reservation caps aggregate staging, registration and in-flight bytes, as well as per-Rail active requests and bytes. The documented `RLIMIT_MEMLOCK` headroom can reject an oversized concurrent request before dispatch, as observed in the 256 MiB/concurrency-2 RXE preflight. No same-request transparent retry is attempted after a required Rail fails.

**Completion and publication.** The scoped worker group returns only after every started task has terminated. The reader checks each task's packed length and completed stripe count, assembles multiple Rail outputs, checks optional per-stripe xxh3 and holds the staged result private while it repeats `LookupObject`. A changed descriptor or placement returns an error. Only `commit_if_unchanged` copies the validated full object to `C`; the cancellation mutex spans that copy. A failed Rail, checksum, version or reservation leaves `C` untouched.

**Retirement.** The client drops its QP before its registered receive buffer on both success and error paths. Control timeouts retire the connection, avoiding a stale response or CQE being mistaken for a later request. The server retains uncertain slab extents, cache pins or `(MR, Bytes)` sources until QP destruction and retires its connection when CQ state is uncertain. Both the new stripe-subset and older full-object GET path use the retirement discipline. These rules are necessary because a failed control exchange alone does not certify that posted WRs have stopped.

## 4. Evaluation method

We separate correctness, physical single-HCA cost attribution and software multi-Rail scaling.

**Correctness environment.** Two Ubuntu 22.04 KVM guests on one host used two independent virtio Ethernet pairs, Linux bridges and `rdma_rxe` devices (`rxe_s0/rxe_c0` and `rxe_s1/rxe_c1`). The two paths could be discovered, enabled, disabled and faulted independently. Both stripe directories reside on one guest virtual disk, so this setup cannot establish HCA offload or independent disk supply. A 64 MiB/16-stripe object was reconstructed with 32 MiB per Rail and a matching full-object hash. The [fault manifest](../../kv-service/benchmarks/results/softroce-vm-test-manifest.json) records dead-listener, stale-generation, in-flight cancellation, stripe corruption, late second-Rail WRITE, connection retirement and resource-limit cases with raw log hashes. The one-Rail no-copy change subsequently passed 46 client unit tests (one Mock benchmark remained ignored), a single-Rail physical Verbs read, and a dual-RXE object reconstruction.

**Physical cost environment.** Node1 served node2 through one ConnectX-6 Dx `mlx5_1` port 1/GID 3 (100 Gb/s, NUMA 1). The 64 MiB object used sixteen 4 MiB stripes in two directories on the same Intel SATA SSD. A separate one-QP, 1 MiB-message `ib_write_bw` calibration ran three independent eight-second trials; median throughput was 97.94 Gb/s. The application measurement includes two lookups, connection, MR, server work, checksum and final publication; dividing link throughput by application payload throughput would not predict speedup. A research-only opt-in trace measured nested client stages, then a ten-block AB/BA comparison used the same server/object with the original and no-copy one-Rail client binaries. Each process performed one warmup plus five measured reads. The [raw stage and revision data](baseline-ablation-results.md) preserve exact binary hashes, object hashes and per-request logs.

**RXE throughput environment.** We measured 64 and 256 MiB objects at concurrency 1, 64 MiB at concurrency 4 and 256 MiB at concurrency 2. Each cell has ten alternating one/two-Rail process blocks. A sequential process performs one warmup and five measured reads; a concurrent process performs one warmup and three measured batches. The one/two ratio is computed from raw arm medians or batch wall sums. A seeded 20,000-draw percentile bootstrap resamples the ten paired **process blocks** to describe uncertainty; reads within a process are not treated as independent. Both arms of the 256 MiB/concurrency-2 cell used unlimited guest `RLIMIT_MEMLOCK` because the default cap rejected the required registrations. The raw per-arm logs, environment records, CPU, RSS, Rail byte counts and `SHA256SUMS` are checked in. The original and optimized code revisions ran in different VM sessions, so only within-revision one/two-Rail pairs are experimental comparisons; the physical AB/BA revision test isolates the copy change.

## 5. Results

### 5.1 Functionality and failure semantics

The two RXE Rails restored a 64 MiB object with 32 MiB attributed to each Rail and the same whole-object xxh3 as the one-Rail result. Fault receipts show that an unavailable second listener, old generation, corrupted stripe checksum and cancellation return errors while preserving a sentinel caller buffer; a late second-Rail WRITE after the first Rail completes does not corrupt a reused buffer in the injected trace. A prior stale-reply control test was red before the client retired the connection on timeout and green afterward. These are tested execution classes, not exhaustive interleaving coverage. The [safety argument](safety-contract.md) names the remaining process-crash and provider assumptions.

### 5.2 The available physical read is not a demonstrated wire bottleneck

The link-calibration median of 97.94 Gb/s is about 11.40 GiB/s of WRITE microbenchmark throughput. An earlier full ContextStore 64 MiB single-Rail read had a 163.271 ms median, or 0.383 GiB/s payload. The approximately 29.8× gap is a *capacity comparison between different workloads*. In a later same-object client trace, the original one-Rail read's marginal medians included 32.2 ms of receive-buffer initialization, 53.2 ms of assembly, 19.7 ms of final publication and 19.2 ms in composite GET/CQ. All ten measured traced requests closed their nested timing accounts within 1.66% of CLI wall time. GET/CQ includes remote service and is not pure wire time; server subset diagnostics lack a shared request ID. The evidence rules out claiming that this application run saturated one NIC, while leaving open whether another workload could.

### 5.3 A fair one-Rail baseline changes the result

The no-copy one-Rail handoff removes the original assembly allocation/copy while preserving the read contract. In ten paired physical-HCA code-revision blocks, the geometric mean of original/new latency ratios was **1.426×** (95% block-bootstrap interval **1.342–1.534×**); all ten blocks favored the corrected baseline. The median of process medians fell from 144.802 to 108.127 ms. Median CPU user+system per read fell from 120.2 to 68.5 ms, and client peak RSS from 199.2 to 135.3 MiB. Traced assembly time fell from roughly 53 ms to effectively zero in its separate stage pilot. Figure [physical revision ablation](figures/physical-single-rail-nocopy-ablation.svg) displays every paired block and its order.

The original software-RXE matrix had shown modest apparent two-Rail gains (1.038–1.101× geometric means across four cells). Rerunning the **same four cells** with the corrected one-Rail implementation produced a different conclusion:

This does not show that multi-Rail transfer is inherently slower: the guests share a host and disk, the software RXE paths consume CPU, and the tested application is not known to saturate one physical link. It shows that the previous gain was not robust to a reasonable baseline correction.

## 6. Discussion and limitations

The safety mechanism imposes real costs. Private receive regions keep partial WRITEs away from the caller, but independent QPs and per-Rail buffers add setup, memory registration, memory initialization and CPU work. Multiple Rail results still require an ordered private assembly pass before version recheck and publication. The single-Rail correction demonstrates the impact of just one unnecessary pass. A future direct-to-ordered-staging multi-Rail path could remove that pass while preserving caller-buffer isolation, but it would require disjoint write ownership, safe per-device MR registration and a dummy target for unowned SGE entries. It must pass the same late-WRITE/cancel/partial-completion tests before being used as a performance baseline. We have not implemented or evaluated it.

Several bounds remain. The physical cluster offered only one online HCA path per node; no physical dual-HCA scaling claim is possible. The RXE guests share physical CPUs and one virtual disk, and we did not collect matched per-link byte, disk-source and CPU/IRQ counters for every process block. Ten launched blocks are a modest sample within one VM-host configuration, and the bootstrap intervals do not measure host-to-host variability or correct for four exploratory cells. The two metadata lookups establish an observed version identity, not a promise that no rewrite occurs after the second lookup. Descriptors without checksums cannot detect arbitrary silent bit corruption. Provider behavior under process crash or abrupt device reset remains untested, and the safety argument is not machine checked. The code is an unmerged draft; maintainer review and independent reproduction remain separate from our local evidence.

## 7. Related work

Multi-Rail transport is established in [UCX's documentation](https://github.com/openucx/ucx/blob/master/docs/source/faq.md). [TENT](https://arxiv.org/abs/2604.00368) studies telemetry-driven slice spraying and fault rerouting for disaggregated LLM service, a stronger scheduling contribution than our static weighted assignment. [Mooncake](https://arxiv.org/abs/2407.00079) and [NIXL](https://docs.nvidia.com/nixl/getting-started/architecture/) address RDMA-based KV movement and transfer capabilities. [RFC 5042](https://datatracker.ietf.org/doc/rfc5042/) describes RDMA security and memory-key considerations. Our distinction is the specific integration of versioned striped-object checks, caller-buffer atomicity, uncertain QP/source retirement and a measured account of their cost in ContextStore. We do not claim invention of multi-Rail transport, endpoint advertisement, static striping or RDMA memory-lifetime principles.

## 8. Conclusion

ContextStore can read one versioned striped object through two independently faultable RDMA Rails without changing its disk layout or caller API, and the tested failures leave the caller's buffer intact. In the available environments, safe multi-Rail functionality did not translate into demonstrated hardware bandwidth aggregation. A redundant one-Rail copy initially made two software Rails look faster; removing it produced a faster physical one-Rail path and an RXE matrix without a stable dual-Rail gain. The next research step is a lower-copy multi-Rail staging design coupled to a genuinely network-limited physical setup and a stronger state-interleaving check. Until then, the reproducible artifact and the corrected negative result are the defensible contribution.
