# Failure-Atomic Multi-Rail Reads for Versioned KV-Cache Objects: A ContextStore Experience

**Manuscript status:** evidence-bounded draft, updated 2026-10-12. The independent upstream [ContextStore draft PR #32](https://github.com/DaoCloud/ContextStore/pull/32) remains unmerged at `c1c1de1`; this separate research branch contains the one-Rail baseline correction, opt-in direct ordered staging, model and evaluation. No maintainer acceptance, implementation-level formal proof, physical dual-HCA aggregation or conference submission is implied.

## Abstract

Large KV-cache objects may already be striped across storage devices. Reading one object through several RDMA paths must preserve a single version and all-or-nothing caller visibility even when a path times out or a WRITE arrives late. We implemented an opt-in multi-Rail read inside ContextStore's Rust SDK and KVService without changing the disk layout or caller API. The client matches owner-bound endpoints to local Verbs devices, assigns stripes to request-private registered targets, joins all workers, validates coverage/checksums and rechecks object identity before one caller-buffer publication. A direct mode lets two Rails receive into disjoint slices of one private ordered vector while retaining the same failure gate. Client/server cleanup fails-stop if the provider cannot destroy a QP or deregister an MR. Two isolated Soft-RoCE paths pass object reconstruction, cancellation, disconnect and delayed-WRITE injections; a separate concurrent-overwrite run observed eight reads whose pre/post-transfer lookups saw increasing Generations, all safely rejected without changing the caller buffer. A bounded two-Rail abstraction exhausts 19,657 states under stated assumptions, not a proof of the Rust/Verbs program. A physical single-HCA code-revision ablation first exposed a misleading baseline: removing a redundant one-Rail copy improved latency 1.426× in ten paired blocks and erased an earlier apparent RXE dual-Rail gain. Against that corrected baseline, ten balanced five-arm blocks per object show direct staging versus a **same-scheduler packed control** at 1.100× throughput for 64 MiB (95% block-bootstrap 1.048–1.161×) and 1.161× for 256 MiB (1.117–1.209×), with lower CPU/RSS and unchanged registered payload. The 256 MiB object uses a different server source fallback, so the size trend is not isolated. This is software-path evidence; the available application does not demonstrate single-NIC saturation or physical multi-HCA aggregation.

## 1. Introduction

KV-cache loading is an object read with several coupled identities: the bytes, the layout that names each stripe, and the version the caller expects. ContextStore can stripe a large object across devices. If storage supply exceeds one network path, independent RDMA Rails are an attractive way to aggregate bandwidth without rewriting the disk layout. Yet each Rail introduces a QP/CQ, registered target memory, a separate control exchange and an asynchronous completion history. An error on one Rail does not prove that another Rail's WRITE has stopped. Directly writing into the caller's destination would make a partially loaded object visible; freeing a timed-out target can expose a reused allocation to a delayed WRITE.

The design question is therefore broader than how to distribute stripes. A successful request needs complete coverage of one object version, a failure-atomic publication point, and safe memory retirement on both sides of the WRITE. It also needs a performance comparison that starts from the best reasonable one-Rail implementation. We built those checks inside ContextStore's Rust SDK and KVService path and measured them on real Verbs, including two independent RXE devices. The implementation keeps one-Rail deployment and older endpoint configurations available. The separate Python/FFI direct-buffer API is outside this read contract.

Three observations shape this paper. First, an object-level safety contract needs *both* DMA quiescence and private staging ownership through publication; a bounded model and real fault tests expose distinct violations of those rules. Second, the available physical application's single HCA is **not demonstrated** to be saturated: a link-capacity microbenchmark and the application run have very different rates and work. Third, copying determines the interpretation of software-RXE results: a redundant one-Rail copy created a false dual-Rail gain, while a same-scheduler direct multi-Rail stage removes another full-object pass and yields a bounded software-path benefit.

The contributions are an integrated implementation and independently inspectable evidence rather than a claim that multi-Rail transfer is new. We provide (1) a failure-atomic, version-checked read path and a reviewed, bounded ownership model with explicit provider assumptions; (2) disjoint direct ordered staging that preserves that contract while avoiding packed two-Rail assembly; and (3) real-Verbs fault receipts, a physical one-Rail baseline correction and repeated five-arm RXE comparisons that isolate scheduling from the net staging effect. The [claim ledger](claim-evidence.md) marks which statements are tests, measurements, hypotheses or unsupported claims.

## 2. Read contract and failure model

Let `V0` be the descriptor and placement returned before transfer and `V1` those returned after all Rail workers terminate. A published read requires identical `(object_handle, generation, ETag, layout_version, placement)` at both lookups, exact object length, a complete nonoverlapping stripe map, exact per-Rail response counts and every supplied checksum to match. The first lookup fixes a candidate snapshot; the second rejects a rewrite observed during transfer. This contract does not promise that the value remains current after the second lookup. It also assumes a new object version changes the metadata identity and that bytes of a named version are not silently mutated without a checksum failure.

Let `C` be the caller buffer, `P_r` a private registered destination for Rail `r`, `Q_r` its QP/CQ, and `S_r` a server source extent/MR. `C` is never an RDMA target. On a control timeout or uncertain completion, the client retires `Q_r` before deregistering or reusing `P_r`; the server retains `S_r` until the corresponding QP is destroyed. Every started worker joins before request-owned staging can be released. Direct mode has a second ownership rule: even after all QPs retire, the ordered private vector cannot be recycled until validation and final publication or failure. An unsuccessful QP destruction or MR deregistration triggers fail-stop before memory reuse. The publication copy runs only after all checks and under a mutex shared with cancellation. The [bilingual mechanism figure](figures/safety-lifecycle-2026-10-09-v2/contextstore-safe-rail-read_en.svg) depicts the private-buffer path and failure lifetime; [the direct-staging design](direct-ordered-staging-design.md) describes its disjoint-slice refinement. The [implementation-linked safety contract](safety-contract.md) and [bounded state exploration](safety-model-plan.md) state their provider assumptions and limits. Neither is a proof of the Rust/Verbs implementation or process-crash recovery.

This lifetime claim is for the Rust SDK multi-Rail implementation and its KVService server path. ContextStore's separate `rdma-ffi`/Python API exposes caller-owned registered buffers and has a different teardown design; it is not covered by this paper's model or fail-stop claim.

The first version stages each Rail's compact receive buffer, then assembles the ordered object into a separate private vector. A later optimization moves the sole Rail's receive vector directly into staged ownership when that one task covers the complete object and each packed offset equals its object offset. The QP/MR have already retired before the vector moves; checksums, version recheck and final caller copy remain unchanged. This is a safe baseline correction, not a change to the multi-Rail path. The [design and controlled ablation](baseline-ablation-results.md) record the precondition and its measured effect.

## 3. ContextStore integration

**Path discovery.** Optional placement capabilities bind a real storage owner and advertised endpoint to fabric/listener pairs. The local configuration maps those fabrics to a Verbs device, port and GID. The reader rejects ambiguous owner/listener mappings, missing paths and unexpected placement changes before moving bytes. Manual explicit routes preserve older servers; a single configured Rail uses the same API. This capability exchange is compatibility plumbing, not a novelty claim about routing.

**Scheduling and transfer.** The original planner retains the stored stripe order and layout, assigns whole stripes among eligible Rails by weighted assigned bytes and creates per-Rail packed receive targets. The opt-in direct mode applies only to a single nonempty storage owner with multiple eligible paths: it partitions consecutive stripe runs by positive route weight, borrows disjoint slices from one private ordered vector, registers each target slice plus a dummy MR, and issues the same stripe-subset SGE request. A packed-contiguous control uses exactly the same stripe assignment while retaining assembly. Other layouts fall back to the original planner; both new toggles default off. Each worker owns its QP/CQ; the server validates descriptor identity, requested indices, owners and ranges. A shared reservation caps aggregate staging, registration and in-flight bytes, as well as per-Rail active requests and bytes. The documented `RLIMIT_MEMLOCK` headroom can reject an oversized concurrent request before dispatch, as observed in the 256 MiB/concurrency-2 RXE preflight. No same-request transparent retry is attempted after a required Rail fails.

**Completion and publication.** The scoped worker group returns only after every started task has terminated. The reader checks each task's expected length and completed stripe count, assembles packed Rail outputs or retains the already ordered direct vector, checks optional per-stripe xxh3 and holds the staged result private while it repeats `LookupObject`. A changed descriptor or placement returns an error. Only `commit_if_unchanged` copies the validated full object to `C`; the cancellation mutex spans that copy. A failed Rail, checksum, version or reservation leaves `C` untouched.

**Retirement.** The client drops its QP before its registered receive buffer on both success and error paths. Control timeouts retire the connection, avoiding a stale response or CQE being mistaken for a later request. The server retains uncertain slab extents, cache pins or `(MR, Bytes)` sources until QP destruction and retires its connection when CQ state is uncertain. Both stripe-subset and older full-object GET use the retirement discipline. Client/server destructors now abort on unsuccessful provider QP destruction or MR deregistration; this trades availability for a bounded memory-lifetime claim and its error branch has not been provider-fault injected.

**Cost hypothesis.** With fixed source and stripe assignment, one read can be decomposed approximately into `Lookup0 + plan/admission + max_r(connect_r + register_r + GET/CQ_r + retire_r) + assembly + checksum + Lookup1 + publication`. This is a diagnostic equation, not a claim that server work or Rail stages never overlap. Packed two-Rail mode budgets an object-sized receive total **and** an object-sized ordered staging vector, plus dummy regions. Direct mode budgets one object-sized vector plus dummy regions; both still pay a final caller publication copy. The packed-contiguous/direct comparison holds each Rail's stripe set constant and tests whether removing assembly is worth its different target/dummy registration and teardown. A per-stage trace is needed to attribute individual terms; a total-time ratio alone cannot identify pure memory-copy cost.

Figure [packed versus direct staging](figures/direct-vs-packed-2026-10-09-v1/contextstore-direct-vs-packed_en.svg) makes the fixed stripe assignment and changed memory movement explicit. Its 8/8 split is the equal-weight 16-stripe example, not a universal placement policy; the [bilingual scene source](figures/direct-vs-packed-scene.json) keeps it editable.

## 4. Evaluation method

We separate correctness, physical single-HCA cost attribution and software multi-Rail scaling.

**Correctness environment.** Two Ubuntu 22.04 KVM guests on one host used two independent virtio Ethernet pairs, Linux bridges and `rdma_rxe` devices (`rxe_s0/rxe_c0` and `rxe_s1/rxe_c1`). The two paths could be discovered, enabled, disabled and faulted independently. Both stripe directories reside on one guest virtual disk, so this setup cannot establish HCA offload or independent disk supply. A 64 MiB/16-stripe object was reconstructed with 32 MiB per Rail and a matching full-object hash. The earlier [fault manifest](../../kv-service/benchmarks/results/softroce-vm-test-manifest.json) records dead-listener, stale-generation, checksum, cancellation, late WRITE and resource-limit cases. The final direct-staging build passed 53 Rust client unit tests (one Mock benchmark remained ignored) and 102 server unit tests with RDMA enabled. Its [new RXE fault receipts](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/faults/) repeat direct-mode cancellation, dead second listener and late second-Rail WRITE. A test-only Verbs interposer injected QP-destroy and MR-deregister error returns with stderr closed; both aborted before further cleanup and a normal request recovered. That tests the error branch, not an actual provider fault.

**Physical cost environment.** Node1 served node2 through one ConnectX-6 Dx `mlx5_1` port 1/GID 3 (100 Gb/s, NUMA 1). The 64 MiB object used sixteen 4 MiB stripes in two directories on the same Intel SATA SSD. A separate one-QP, 1 MiB-message `ib_write_bw` calibration ran three independent eight-second trials; median throughput was 97.94 Gb/s. The application measurement includes two lookups, connection, MR, server work, checksum and final publication; dividing link throughput by application payload throughput would not predict speedup. A research-only opt-in trace measured nested client stages, then a ten-block AB/BA comparison used the same server/object with the original and no-copy one-Rail client binaries. Each process performed one warmup plus five measured reads. The [raw stage and revision data](baseline-ablation-results.md) preserve exact binary hashes, object hashes and per-request logs.

**RXE throughput environment.** We measured 64 and 256 MiB objects at concurrency 1, 64 MiB at concurrency 4 and 256 MiB at concurrency 2. Each cell has ten alternating one/two-Rail process blocks. A sequential process performs one warmup and five measured reads; a concurrent process performs one warmup and three measured batches. The one/two ratio is computed from raw arm medians or batch wall sums. A seeded 20,000-draw percentile bootstrap resamples the ten paired **process blocks** to describe uncertainty; reads within a process are not treated as independent. Both arms of the 256 MiB/concurrency-2 cell used unlimited guest `RLIMIT_MEMLOCK` because the default cap rejected the required registrations. The raw per-arm logs, environment records, CPU, RSS, Rail byte counts and `SHA256SUMS` are checked in. The original and optimized code revisions ran in different VM sessions, so only within-revision one/two-Rail pairs are experimental comparisons; the physical AB/BA revision test isolates the copy change.

**Direct-staging five-arm control.** A separate same-binary RXE experiment has optimized one Rail through each of `rxe_c0` and `rxe_c1`, original greedy packed two-Rail, contiguous-plan packed two-Rail, and contiguous-plan direct two-Rail. Ten launched blocks use five cyclic arm orders and their reverses, placing each arm twice in every position. Each process has one warmup and five complete-object reads. The predeclared primary contrast is direct versus packed-contiguous: both assign the same stripes to the same Rails, so it measures the net staging implementation package without a scheduling change. The collector records the *effective* rather than merely requested mode, exact descriptor and placement fingerprints before and after each arm, per-Rail stripe indices/bytes, whole-object hash, client CPU and RSS; an independent audit recomputes block medians and paired log ratios from raw logs. The 64 and 256 MiB objects differ in server source behavior: the latter exceeds the 128 MiB RDMA slab and takes the registered-buffer fallback. Therefore a cross-size trend cannot be attributed to size alone. Both are software-RXE experiments on one virtual disk and do not measure hardware multi-NIC aggregation.

## 5. Results

### 5.1 Functionality and failure semantics

The two RXE Rails restored a 64 MiB object with 32 MiB attributed to each Rail and the same whole-object xxh3 as the one-Rail result. Fault receipts show that an unavailable second listener, old generation, corrupted stripe checksum and cancellation return errors while preserving a sentinel caller buffer; a late second-Rail WRITE after the first Rail completes does not corrupt a reused buffer in the injected trace. The final direct mode repeated cancellation, dead-listener and delayed-WRITE checks. The server's 3 s injected delay and 2 s CQ deadline produced `0/32` final completions and connection retirement, while the caller sentinel stayed intact. A prior stale-reply control was red before connection retirement on timeout and green afterward.

A [unique-Generation concurrent overwrite campaign](rewrite-race-and-server-failstop-2026-10-09.md) used two 8 MiB process runs. Each of 30 committed writes had distinct bytes; the SDK logged the actual Generation accepted after its second lookup and publication. The writer recorded the **PUT response time separately from its later metadata lookup**. Among 40 total read attempts, **31** read intervals intersected an SDK PUT method call whose start timestamp followed payload allocation and segmentation: six returned a byte-for-byte complete value whose encoded Generation equaled the SDK's accepted Generation, while 25 safely rejected and kept the caller sentinel. Two-Rail activity and zero terminal reservations were logged. A Linux release-build receipt matched 20 source files to commit `9209d502` before and after compilation and pinned the resulting binary to each launch-time hash. These timestamps prove overlap with the SDK method call, not with the server commit point. A separate physical node reproduced the audit JSON. An earlier two-run campaign yielded 36 intersections with a *wider* payload-preparation-plus-SDK-call interval; three still earlier runs yielded 51 intersections with a PUT-plus-Lookup round. Neither count is pooled with the 31 SDK-call intersections; a still earlier A/B campaign reused content and cannot detect mixing same-content Generations. Isolated server-side test-only QP-destroy and MR-deregister error-return injections each exited with `SIGABRT` before continuing cleanup; launch-time server/shim/config/script/client hashes and a normal recovery read are retained. This closes the previously untested **reported-error branches**, not genuine provider failure. The [revised explicit-state model](safety-model-plan.md) exhausts 19,657 two-Rail states with no violation of its stated invariants and gives six weakened-guard counterexamples. These are tested execution classes and an abstract model, not exhaustive implementation-level interleaving coverage. The [code-to-model map](code-to-model-refinement-map-2026-10-09.md) names process-crash, provider and Python/FFI scope limits.

Figure [SDK-call/read interval timeline](figures/unique-generation-sdk-call-race-2026-10-09.svg) shows every interval in one run and the audited overlap classes across both runs. The orange bands end at the **PUT response**, avoiding the earlier wider writer-round interpretation; the nine attempts without measured SDK-call overlap are shown separately. The editable [plot source](../../kv-service/verification/plot_unique_race.py) reads the saved timestamp logs rather than invented event times.

A separate [Generation-transition witness run](generation-transition-witness-2026-10-12.md) addresses the remaining concurrency inference without sharing a server clock. The sequential reader queried identity before and after private-staged RDMA transfer; eight rejected reads observed strictly increasing Generation pairs (for example, 1→2 and 13→14), while the caller sentinel stayed unchanged. In this single-writer/no-delete run, monotonic Generation allocation and atomic Redis metadata replacement imply a metadata commit between each pair of lookup observations. The run had 20 SDK-call-overlapping reads: ten complete accepts, eight Generation-change rejects and two stale-descriptor rejects. Its source snapshot and launched binary were audited against commit `f1a3fbf`; a second physical node reproduced the audit JSON. This establishes actual metadata transitions during those read methods, without placing the commit inside the RDMA WRITE interval. The one run is not pooled with the preceding two-run campaign or used as a failure-rate estimate.

### 5.2 The available physical read is not a demonstrated wire bottleneck

The link-calibration median of 97.94 Gb/s is about 11.40 GiB/s of WRITE microbenchmark throughput. An earlier full ContextStore 64 MiB single-Rail read had a 163.271 ms median, or 0.383 GiB/s payload. The approximately 29.8× gap is a *capacity comparison between different workloads*. In a later same-object client trace, the original one-Rail read's marginal medians included 32.2 ms of receive-buffer initialization, 53.2 ms of assembly, 19.7 ms of final publication and 19.2 ms in composite GET/CQ. All ten measured traced requests closed their nested timing accounts within 1.66% of CLI wall time. GET/CQ includes remote service and is not pure wire time; server subset diagnostics lack a shared request ID. The evidence rules out claiming that this application run saturated one NIC, while leaving open whether another workload could.

### 5.3 A fair one-Rail baseline changes the result

The no-copy one-Rail handoff removes the original assembly allocation/copy while preserving the read contract. In ten paired physical-HCA code-revision blocks, the geometric mean of original/new latency ratios was **1.426×** (95% block-bootstrap interval **1.342–1.534×**); all ten blocks favored the corrected baseline. The median of process medians fell from 144.802 to 108.127 ms. Median CPU user+system per read fell from 120.2 to 68.5 ms, and client peak RSS from 199.2 to 135.3 MiB. Traced assembly time fell from roughly 53 ms to effectively zero in its separate stage pilot. Figure [physical revision ablation](figures/physical-single-rail-nocopy-ablation.svg) displays every paired block and its order.

The original software-RXE matrix had shown modest apparent two-Rail gains (1.038–1.101× geometric means across four cells). Rerunning the **same four cells** with the corrected one-Rail implementation produced a different conclusion:

The 64 MiB sequential cell consistently favors one Rail; the other three intervals cross parity. CPU and peak RSS rise with two Rails in every cell. This does not show that multi-Rail transfer is inherently slower: the guests share a host and disk, the software RXE paths consume CPU, and the tested application is not known to saturate one physical link. It shows that the previous gain was not robust to a reasonable baseline correction.

### 5.4 Direct staging reduces software-path work under the same stripe plan

The opt-in direct mode removes the packed two-Rail assembly pass while preserving a private caller publication. We compared it with packed-contiguous mode, which uses the **identical stripe sets on the identical Rails**, plus both optimized single-Rail paths and original packed-greedy mode. The [full evidence and audit](direct-staging-eval-2026-10-09.md) and paired-block figures ([64 MiB](figures/rail-five-arm-final-64-2026-10-09.svg), [256 MiB](figures/rail-five-arm-final-256-2026-10-09.svg)) retain all wins and losses.

| Object | Direct / same-plan packed throughput | Direct / one Rail `rxe_c0` | Direct / one Rail `rxe_c1` | CPU ms/read, packed-contiguous → direct | Peak RSS MiB, packed-contiguous → direct |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 MiB | **1.100×** [1.048, 1.161] | 1.073× [1.013, 1.133] | 1.085× [1.064, 1.112] | 123.9 → 76.5 | 206.3 → 142.5 |
| 256 MiB | **1.161×** [1.117, 1.209] | 1.126× [1.048, 1.204] | 1.149× [1.068, 1.228] | 433.6 → 259.4 | 782.5 → 526.6 |

Values in brackets are 95% block-bootstrap intervals over ten launched process blocks; the primary same-plan contrast was predeclared, while one-Rail comparisons are secondary. Process CPU is amortized over all completed reads including warmup and setup; throughput uses measured-read medians. Both packed-contiguous and direct have the same sum of per-Rail peak registered bytes (72 MiB at 64 MiB; 264 MiB at 256 MiB) and the same 64/256 MiB in-flight payload reservation. This supports a reduction in software memory movement and host memory footprint, not a reduction in registered payload or evidence of a faster physical NIC. A separate three-read stage pilot measured packed assembly at a 75.9 ms median and direct assembly at zero; direct checksum time was higher, so total-time improvement remains a net mechanism effect.

An earlier near-identical normal-path build gave 1.121× and 1.134× for the same-plan primary contrast at 64 and 256 MiB. Its 64 MiB direct/`rxe_c0` interval crossed 1, despite the final build's interval above 1. This [raw replication](../../kv-service/benchmarks/results/paper-direct-final-2026-10-09/replication-v2/64mib/audit.json) shows that a single-Rail superiority claim at 64 MiB is sensitive to run conditions. The 256 MiB object used a registered-buffer server fallback because it exceeded the 128 MiB slab; the apparent size trend is confounded with source mode.

## 6. Discussion and limitations

The safety mechanism imposes real costs. Private receive regions keep partial WRITEs away from the caller, but independent QPs and per-Rail buffers add setup, memory registration, memory initialization and CPU work. Packed multi-Rail reads require an ordered private assembly pass before version recheck and publication. The one-Rail handoff demonstrated the cost of an unnecessary pass. We subsequently implemented direct ordered staging for eligible multi-Rail single-owner objects; the disjoint-slice rule removes that assembly copy while preserving caller isolation. Its fair packed-contiguous control is essential because the direct mode also changes stripe scheduling. Any measured benefit is the **net path package**, including allocation and MR differences, not an isolated memcpy effect.

Several bounds remain. A [fresh read-only inventory of all seven physical SKV nodes](physical-hca-availability-2026-10-09.md) found two enumerated Verbs device names per node but only `mlx5_1/1` ACTIVE/LINK_UP on each; no physical dual-HCA scaling claim is possible. A two-QP/one-HCA control is also missing, so any future two-HCA gain must first be separated from mere QP/thread parallelism. The RXE guests share physical CPUs and one virtual disk, and we did not collect matched per-link byte, disk-source and CPU/IRQ counters for every process block. The 256 MiB fallback changes source mode relative to 64 MiB. Ten launched blocks are a modest sample within one VM-host configuration; two normal-path sessions agree on the primary same-plan benefit but vary on the 64 MiB single-Rail contrast. Bootstrap intervals do not measure host-to-host variability or correct for secondary comparisons. The two metadata lookups establish an observed version identity, not a promise that no rewrite occurs after the second lookup. Descriptors without checksums cannot detect arbitrary silent bit corruption. The bounded explorer assumes successful provider retirement, truthful coverage events and a simplified version space; a test-only error-return interposer does not validate firmware behavior. Process crash, abrupt device reset and the separate Python/FFI external-buffer path remain outside the lifetime claim. The research branch is unmerged; maintainer review and independent reproduction remain separate from local evidence.

## 7. Related work

Multi-Rail transport is established in [UCX's documentation](https://github.com/openucx/ucx/blob/master/docs/source/faq.md). More directly, [Mooncake's FAST 2025 paper](https://www.usenix.org/system/files/fast25-qin.pdf) describes one transfer sliced at 16 KB across multiple RDMA NICs, topology-aware local/remote path selection, endpoint pooling, alternative-path resubmission on connection failure, and physical 4×200 Gb/s and 8×400 Gb/s transfer experiments (§3.2.3, §5.4). [TENT](https://arxiv.org/abs/2604.00368) studies telemetry-driven slice spraying and fault rerouting for disaggregated LLM service, a stronger scheduling contribution than our static weighted assignment. [NIXL](https://docs.nvidia.com/nixl/getting-started/architecture/) addresses transfer capabilities and backend selection. [RFC 5042](https://datatracker.ietf.org/doc/rfc5042/) describes RDMA security and memory-key considerations; [Pilaf](https://www.usenix.org/system/files/conference/atc13/atc13-mitchell.pdf) already checks races in one-sided key-value reads. Our possible distinction is the **specified and checked** composition of versioned disk stripes, caller-buffer atomicity and uncertain QP/source retirement in ContextStore. The Mooncake paper does not state this exact object-read contract, which is not evidence that its implementation is unsafe. We do not claim invention of multi-NIC slicing, zero-copy transfer, endpoint pooling, topology-aware choice, static striping or RDMA memory-lifetime principles. The [six-paper methods audit](top-venue-methods.md) details the direct comparison and experiment gate.

## 8. Conclusion

ContextStore can read one versioned striped object through two independently faultable RDMA Rails without changing its disk layout or caller API, and the tested failures leave the caller's buffer intact. A redundant one-Rail copy initially made two software Rails look faster; correcting that baseline improved the physical one-Rail read and exposed the packed multi-Rail overhead. Direct ordered staging then removed the two-Rail assembly pass and improved the **same-plan software-RXE** path at both tested sizes while preserving the object publication contract. The bounded model and error-return injection sharpen the lifetime argument without proving the full Rust/provider implementation. Physical dual-HCA aggregation remains unmeasured. The next decisive experiment needs a verified one-NIC network bottleneck, a two-QP/one-HCA control, two independent HCA paths, matched source/link counters and repeated end-to-end reads before a hardware-performance or top-venue novelty claim is warranted.
